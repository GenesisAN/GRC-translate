# GRC Translate

Translation workbench for GRC, deployed at https://i18n.venodev.com.
Based on [Slush97/grimoire-translate](https://github.com/Slush97/grimoire-translate)
under its MIT license. `upstream.json` records the exact template commit.

## Translation workflow

English sources live in `src/locales/en/translation.json`. Translators edit target
languages in the website, save drafts, and submit a GitHub pull request. Reviewed
translations are merged here; they do not deploy or alter the game automatically.

`catalog-keys.json` maps each opaque JSON identity back to the game's original
message key. Identities include the English wording, so changing the source
invalidates older drafts. Do not edit this file or English sources manually;
update them with `bash eng/rg.sh translations export --checkout <this-checkout>`
from the game repository. Commit and push the resulting diff for source review.

Preserve numbered arguments, including formatting: `{0}`, `{0:N0}`, `{1:0.0}`.
Reordering arguments is allowed; removing, duplicating or changing them is not.
Both the browser and API check these rules; CI also checks JSON integrity.

`python scripts/catalog.py --output dist/translations.csv` generates a UTF-8
Godot CSV. Missing target strings use English. CI publishes this CSV as a build
artifact. Import into the game with an exact Git commit:

```bash
bash eng/rg.sh translations import --checkout <this-checkout> --revision <40-character-commit>
```

The game imports its currently registered languages (`en`, `zh_CN`). Additional
languages can be translated here, but require a separate game change to register
their resources, language menu entries and fonts before shipping.

## Local development

Requires Node 24, pnpm 10.33.0 and Python 3.11+.

```bash
pnpm install --frozen-lockfile
cp .dev.vars.example .dev.vars
pnpm db:migrate:local
pnpm dev
```

Run `pnpm verify:local` to verify catalog loading, placeholder rejection, draft
saving and JSON export against the local database. Evidence is saved under
`.wrangler/local-verification`; its temporary verification draft is removed.

Local development uses `TRANSLATOR_EMAIL`; production always verifies Cloudflare
Access JWTs. Unauthenticated requests never get translator access in production.

## Cloudflare setup

Use this project's own resources, separate from the voting website:

```bash
pnpm exec wrangler d1 create grc-translate
pnpm exec wrangler kv namespace create SESSION
```

Copy the returned IDs into `wrangler.jsonc`. Configure a Cloudflare Access
self-hosted application for `i18n.venodev.com`, with an explicit translator email
allowlist. Set `CF_ACCESS_TEAM` to the Zero Trust team subdomain and
`CF_ACCESS_AUD` to this application's audience tag. Create a fine-grained GitHub
PAT scoped only to `GenesisAN/GRC-translate`, with Contents and Pull requests
read/write permissions. Store it as the Worker secret `GITHUB_TOKEN`.

```bash
pnpm deploy
pnpm exec wrangler secret put CF_ACCESS_TEAM
pnpm exec wrangler secret put CF_ACCESS_AUD
pnpm exec wrangler secret put GITHUB_TOKEN
```

The first deployment remains inaccessible until Access secrets are configured.
The deployment runs type checks, builds, migrates D1, and publishes the Worker
and custom domain. The existing Cloudflare CLI login may need KV permission for
resource creation. All credentials stay outside source control.

GitHub's **Deploy GRC Translate** workflow runs manually. Set repository secrets:
`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `CF_ACCESS_TEAM`, `CF_ACCESS_AUD`,
`GRC_TRANSLATE_GITHUB_TOKEN`. The CF token needs Workers, D1 and bound KV access
for this account. Website deployments and translation review are independent.
